# BUS_S 작업 제안서 (AI 작업 지시용)

> 이 문서는 AI 코딩 에이전트에게 작업을 맡기기 위한 제안서다. 에이전트는 이 문서를 먼저 읽고, 단계(Phase) 순서대로 진행하며, 각 단계의 완료 조건을 충족한 뒤 다음 단계로 넘어간다.

## 1. 목표

부산에서 **출발 정류장 → 도착 정류장**으로 갈 때, 두 정류장을 모두 지나는 버스 노선이 여러 개라면 **지금 어느 버스를 타야 하는지** 하나를 추천하는 모바일 앱.

### 결정 우선순위

1. **혼잡도** — 덜 붐비는 버스
2. **최단 경로** — 두 정류장 사이 소요시간(정류장 수 또는 예상 시간)이 짧은 노선
3. **같은 노선의 다음 버스** — 첫 번째 버스가 붐비면, 같은 노선 다음 버스의 도착시간과 혼잡도를 보고 "보내고 다음 차 타기"를 판단

### 범위

- 포함: 단일 노선 직행(환승 없음), 부산 시내버스, 실시간 도착정보 기반 추천
- 제외(MVP 이후): 환승 경로, 마을버스·광역버스, 도시철도 연계, 로그인/회원
- **개인용 앱**: 스토어 배포 없이 본인 폰(안드로이드)에 직접 설치. 별도 서버 없음.

## 2. 아이디어 검토 결과

### 좋은 점
- 같은 구간에 노선이 겹치는 경우가 부산에 많다(서면·부산역·해운대 축 등). 기존 지도 앱은 "가장 빠른 경로"만 보여 줄 뿐 **"이 정류장에서 지금 어느 버스를 탈지"**는 사용자가 직접 비교해야 한다.
- 환승을 빼면 계산이 단순하다. 경로 탐색이 아니라 **후보 노선 비교** 문제다.

### 핵심 위험 (반드시 Phase 0에서 확인)
| 위험 | 내용 | 대응 |
|---|---|---|
| **혼잡도 데이터 존재 여부** | 서울·경기는 실시간 버스 혼잡도를 공개 API로 제공하지만, 부산 BIMS 공개 API에서 혼잡도(재차인원/혼잡 단계)를 제공하는지 **확인되지 않았다.** 1순위 기준이 데이터 없이 동작할 수 없다. | Phase 0에서 공공데이터포털 부산 버스 API 응답 필드 전수 확인. 없으면 아래 대체안 중 선택 |
| 엄격한 우선순위의 부작용 | 혼잡도를 무조건 1순위로 두면 "15분 뒤 한산한 버스" > "2분 뒤 보통 버스"가 된다. | 혼잡도를 **단계(여유/보통/혼잡/매우혼잡)**로 묶고, **최대 대기시간** 제한을 둔다 (기본 10분, 설정 가능) |
| API 호출 한도 | 공공데이터포털 일일 트래픽 제한 | 1인 사용이라 여유 있음. 앱 내 짧은 캐시(15~30초) + 화면 켜져 있을 때만 새로고침 |
| API 키 관리 | 개인용이라 앱에 키를 넣어도 되지만 저장소에 올라가면 유출 | `.env`에 보관, 커밋 금지 |
| 정류장 방향 혼동 | 같은 이름 정류장이 도로 양쪽에 있음(방향 반대) | 이름이 아닌 **정류소 ID/번호**로 구분, "다음 정류장: OO 방면" 표시 |

### 혼잡도 데이터가 없을 때의 대체안
- A. **추정 혼잡도**: 배차 간격이 벌어진 버스(앞차와 간격이 큰 버스)는 붐빈다는 경험칙으로 추정 — 도착정보만으로 계산 가능
- B. **사용자 제보**: 탑승 후 "붐빔/여유" 한 번 탭 — 데이터가 쌓여야 의미 있음
- C. 혼잡도 기준을 보류하고 최단경로 + 다음 차 비교로 MVP 출시
- 권장: **A로 시작, B를 추가**. 실제 혼잡도 API가 확인되면 교체.

## 3. 추천 알고리즘 (초안)

```
입력: 출발 정류장 S, 도착 정류장 D, 현재시각
1. 후보 노선 = S와 D를 같은 방향 순서로 모두 지나는 노선
2. 각 후보 노선에 대해 S에 도착 예정인 버스 1, 2번째를 조회 (도착시간, 혼잡도)
3. 대기시간 > 최대대기시간 인 버스, 대기시간 < 정류장까지 도보시간 인 버스는 제외
   (출발/도착 정류장이 여러 개면 모든 조합에 대해 1~3 수행)
4. 각 버스 점수 =
     (혼잡도 단계)                       ← 1순위, 단계 낮을수록 좋음
     → 동률이면 (대기시간 + S→D 소요시간)  ← 2순위
5. 같은 노선의 2번째 버스가 1번째보다 혼잡도 단계가 낮고,
   추가 대기가 허용 범위(기본 5분) 이내면 "다음 차 추천" 표시      ← 3순위
6. 1위 버스 + 이유 문구 + 나머지 후보 목록 반환
```

- 추천 로직은 **UI·API와 분리된 순수 함수**로 작성하고 단위 테스트를 붙인다.
- 기준값(단계 구간, 최대 대기, 다음 차 허용 시간)은 설정 파일로 뺀다.

## 4. 기술 스택 (제안)

| 영역 | 선택 | 이유 |
|---|---|---|
| 앱 | React Native + Expo (TypeScript) | 안드로이드·iOS 동시, 빠른 시제품 |
| 서버 | 없음 (앱이 공공 API 직접 호출) | 개인용이라 불필요 |
| 설치 | Expo Go(개발 중) → EAS/로컬 빌드 APK 직접 설치 | 스토어 등록 불필요 |
| 정적 데이터 | 정류장(좌표 포함)·노선 목록을 미리 받아 JSON/SQLite로 번들 | 후보 노선·근처 정류장 계산을 오프라인으로 |
| 추천 로직 | `packages/core` 순수 TS + Vitest | 테스트 쉬움 |
| 지도 | MVP는 지도 없음. 길안내는 카카오맵/네이버지도 앱으로 넘김(딥링크). 지도 화면은 Phase 4 | 지도 SDK 연동 비용 대비 효용 낮음 |

### 정류장 인식 방법
1. **GPS → 근처 정류장**: 정류장 좌표 목록(부산 BIMS 정류소 정보 또는 국토부 TAGO 정류소정보 API의 좌표기반 근접 정류소 조회)에서 반경 300m 이내를 가까운 순으로 표시. 기본 출발지로 자동 선택.
2. **검색**: 정류장 이름 또는 정류소 번호로 검색.
3. **출퇴근 구간 설정** (핵심 기능, 아래 "출퇴근 설정" 참고): 앱을 열면 바로 추천.
4. 지도 앱 연동은 **보내기만** 가능: 카카오맵(`kakaomap://route?...&by=PUBLICTRANSIT`), 네이버지도(`nmap://route/public?...`) 딥링크로 길안내를 열 수 있으나, 이 앱들의 버스 데이터를 받아올 수는 없다.

### 출퇴근 설정
출퇴근하는 사람은 쓰는 정류장이 정해져 있으므로, 처음 한 번 설정하면 **앱을 열자마자 추천이 뜨는 것**을 기본 화면으로 한다.

| 설정 항목 | 내용 | 예시 |
|---|---|---|
| 구간 이름 | 자유 입력 | 출근, 퇴근, 본가 |
| 출발 정류장 | **여러 개 지정 가능** (집 앞 정류장 2곳 중 나은 쪽) | OO아파트앞, OO시장 |
| 도착 정류장 | 여러 개 지정 가능 (회사 근처 아무 정류장이나 OK) | 서면역, 부전시장 |
| 이용 노선 | 자동(후보 전부) 또는 직접 체크해서 제한 | 자동 |
| 자동 선택 시간대 | 요일 + 시간대에 이 구간을 기본으로 띄움 | 평일 07:00~09:30 → 출근 |
| 최대 대기시간 | 구간별로 다르게 (아침엔 짧게) | 출근 7분, 퇴근 15분 |
| 정류장까지 도보시간 | 도착 예정 버스 중 걸어가서 못 타는 버스 제외 | 3분 |

- 시간대가 겹치지 않으면 해당 구간 자동 선택, 아무 구간도 안 맞으면 GPS 근처 정류장 화면.
- 출발/도착 정류장이 여러 개면 모든 조합의 후보 노선을 한 번에 비교한다 (도보시간 반영).
- 설정은 기기 내부 저장소(AsyncStorage/SQLite)에 보관. 내보내기/가져오기(JSON)로 폰 교체 시 이전.
- 구간 설정 시 정류장은 GPS 근처 목록·검색에서 고르고, **방향("OO 방면")을 반드시 확인**하게 한다.

## 5. 단계별 작업 지시

### Phase 0 — 데이터 확인 (코드 작성 전, 가장 중요)
- 공공데이터포털(data.go.kr)에서 부산 버스 관련 API를 찾아 목록화: 정류소 검색, 노선 정보, 노선별 경유 정류소, 정류소별 도착정보, 버스 위치
- 각 API를 실제 호출하여 응답 샘플을 `data/samples/`에 저장
- **혼잡도 관련 필드 유무**를 확인하고 `docs/api-notes/congestion.md`에 결론 기록
- 완료 조건: API 목록 표, 샘플 응답, 혼잡도 결론(있음/없음/대체안 선택)

### Phase 1 — 추천 로직 (`packages/core`)
- 정규화된 데이터 타입 정의 (Stop, Route, Arrival, Recommendation)
- 3장 알고리즘 구현 + 테스트(동률, 후보 없음, 전부 혼잡, 다음 차 추천 케이스 포함)
- 완료 조건: 테스트 통과, 샘플 데이터로 CLI 실행 시 추천 결과 출력

### Phase 2 — 데이터 연결 (`app/src/api/`, `scripts/`)
- 정류장(좌표)·노선 경유 정류장 목록을 받아 `data/static/`에 저장하는 스크립트
- 도착정보 API 호출 모듈 → core 입력 형식으로 변환, 캐시 15~30초
- GPS 좌표 → 반경 내 정류장 목록 함수
- 완료 조건: 실제 부산 정류장 쌍으로 추천 결과가 콘솔에 출력

### Phase 3 — 앱 MVP (`app/`)
- 화면:
  ① **홈 = 현재 시간대 구간의 추천 결과** (1위 크게 + 이유 + 후보 목록, 다른 구간 탭 전환)
  ② 출퇴근 구간 설정 (정류장 선택·방향 확인·시간대·대기/도보시간)
  ③ 정류장 검색 / GPS 근처 정류장 (설정 안 된 구간용)
- 30초 자동 새로고침 (화면 켜져 있을 때만)
- 완료 조건: 출근 구간을 설정하고, 평일 아침에 앱을 열면 바로 추천이 뜨는 것을 실제 폰에서 확인

### Phase 4 — 개선
- 사용자 혼잡 제보, 알림("추천 버스 3분 전"), 홈 화면 위젯
- 지도 화면: 카카오맵 JavaScript API를 WebView로 띄워 정류장·버스 위치 표시

## 6. 에이전트 작업 규칙
- 단계마다 결과를 `docs/progress.md`에 날짜와 함께 요약
- API 키·비밀값은 커밋 금지 (`.env`, `.gitignore`)
- 확인되지 않은 API 필드를 추측해서 코드에 넣지 않는다. 모르면 `docs/api-notes/`에 질문으로 남긴다.
- 사람이 결정해야 할 것(대체안 선택, 기준값)은 임의로 정하지 말고 제안 후 확인 받는다.
